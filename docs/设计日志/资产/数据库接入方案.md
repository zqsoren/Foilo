# 资产数据库接入方案（建议稿）

日期：2026-11-17。依据本轮实时 Figma「在侧-资产」与当前仓库源码。用户认为自己调整后的界面已基本可用，本轮只做数据结构评估；以下表名、字段及业务口径是建议，未执行建表、迁移或生产验证。

## 现有项目怎样存数据

项目使用同一个 SQLite 数据库，连接由 [lib/db/index.ts](../../../lib/db/index.ts) 创建，路径由 `MY_LIFE_DB_PATH` 指定，默认是 `data/life-workbench.sqlite`。已启用外键、WAL；项目有 Drizzle，但健身和当前 ToDo 主要使用 better-sqlite3 的参数化 SQL。不能只看 Drizzle 的 schema.ts 判断完整表结构，还要看 migrations.ts 及模块仓库初始化。

| 范围 | 当前实际存储 | 如何分开 |
|---|---|---|
| 共用身份 | users、auth_sessions | 同一个用户ID、同一登录会话，不给资产再建密码表 |
| 当前 ToDo 日程 | todo_workspaces：user_id、revision、payload、updated_at | 每用户一行；payload 是事件、重复规则、聊天、撤销及最近请求号等JSON |
| ToDo 活动与看板 | todo_activity；todo_dashboard_layouts | 活动逐行存；看板layout是JSON；均按user_id读取 |
| 健身共享目录 | gym_exercises、gym_media等 | 动作与媒体供各用户共用，不是私人训练数据 |
| 健身私人记录 | gym_plans、gym_plan_items、gym_workouts、gym_workout_items、gym_sets、gym_set_stages | 计划与训练直接有user_id，子项经父记录归属；部分关联有同用户复合外键 |
| 健身看板与请求 | gym_dashboard_settings、gym_requests、gym_dashboard_requests | 偏好JSON与业务明细分开，按用户存储；revision防覆盖、request_id防重试重复 |

当前ToDo主要入口不是旧 `todos` 简单表。证据：[repository.ts](../../../lib/todo/repository.ts)、[model.ts](../../../lib/todo/model.ts)、[dashboard-store.ts](../../../lib/todo/dashboard-store.ts)、[健身迁移](../../../lib/gym/migration.ts)、[健身store](../../../lib/gym/store.ts)、[桌面store](../../../lib/gym/desktop-store.ts)。

## 隔离到什么程度

- **模块间逻辑分表**：todo_* 与 gym_* 业务表不同，正常模块读写路径分别处理自己的数据；它们不是两个物理数据库，也不是两个数据库账号权限域。备份、连接、迁移入口和底层文件仍共用，表名前缀本身不提供访问控制。
- **用户间应用层隔离**：服务端从有效会话取得user.id，再交给存储函数；客户端不能指定业务所属user_id。读取与修改按user_id限定，子项通过已校验的父记录访问；外键只保证关联有效，不能代替用户权限检查。参见[auth.ts](../../../lib/auth.ts)、[ToDo API](../../../app/api/todo/route.ts)、[健身操作](../../../app/gym/actions.ts)、[健身桌面操作](../../../app/gym/dashboard/actions.ts)。
- **共享与私人明确区分**：身份共享、通用目录共享；日程、训练、资产余额和各模块布局按用户分开。ToDo widget/MCP的令牌仍只对应现有日程入口，不自动取得资产权限。
- **验证范围**：本轮在内存库运行5个现有测试文件、30项通过，包括ToDo/健身跨账号访问、请求去重、并发版本及迁移相关用例。没有登录生产、检查真实余额或执行全接口安全审计；不能把这些测试当作整个系统不存在越权的证明。

## 推荐模型：账户 → 资产明细 → 余额历史

不要按工商银行、小荷包、美元分别增加数据库列，也不要每个银行单独建一张表。类型、银行、币种是字段值；用户增加一张卡就是增加一行。

例：账户“工商银行·工资卡·1234”有明细“人民币活期”28,000和“一年期定期”60,000，账户合计88,000由两项计算。账户本身不再额外存一笔88,000参与总资产，否则会重复计算。支付宝等简单账户自动建一条默认余额明细，用户仍然只填写现有表单一次。

以下为核心表建议；ID使用稳定内部ID，不能用名称、卡尾号或Figma节点ID当主键。

| 表 | 建议字段 | 用途 |
|---|---|---|
| assets_accounts | id、user_id、type_code、institution_code（可空）、name、note、card_last4（可空）、bookkeeping_enabled、archived_at、revision、created_at、updated_at | 具体钱包、银行卡、证券账户等容器；尾号为TEXT，保留前导0；目前界面仅需后4位 |
| assets_positions | id、user_id、account_id、name、category_code、side、currency_code、include_in_totals、archived_at、revision、created_at、updated_at | 一条可计价资产或负债；side为asset/liability，币种在明细层支持同账户多币种 |
| assets_valuations | id、user_id、position_id、as_of_date、amount_minor、source、note、recorded_at、supersedes_id（可空）、voided_at（可空） | 每次录入的余额／当前估值；保留历史，不直接覆盖上一次金额 |

默认余额、定期存款、基金等均属于position，不再在账户上另存权威current_balance。当前金额取该明细截至指定日期的最新有效估值；同日多次记录按recorded_at与id确定顺序。更正和作废需保留原记录及关联，正式交互待确认。

| 辅助数据 | 建议字段及规则 |
|---|---|
| assets_account_types | code、name、group_code、icon_key、form_kind、default_category_code、default_side、sort_order、is_active；共享类型目录，六类固定code。已删类型隐藏而非重建旧账户 |
| 机构／币种／统计类别字典 | 稳定code、名称、图标键或精度等元数据；首版可版本化配置，需动态维护再建字典表。银行不含任何用户余额；图标文件放静态资源，数据库存icon_key |
| assets_fx_rates | id、user_id、from_currency、to_currency、as_of_date、rate_decimal、source、recorded_at；首版建议手动汇率按用户隔离，rate_decimal为规范十进制字符串，不能直接用SQLite浮点SUM；未来官方行情表可独立共享 |
| assets_preferences | user_id、base_currency、layout_json、revision、updated_at；只保存显示偏好，不复制余额数据 |
| assets_requests | user_id、request_id、command_hash、result_json、created_at；组合主键(user_id,request_id)，同号不同内容拒绝，防保存重试生成重复账户或历史 |

不为每个小组件建立独立余额表；所有小组件读取同一组明细和估值。辅助表可随所确认的首版范围落地，不要求为了首版手动记录引入交易、行情或证券持仓系统。

## 表单如何映射

| 页面字段 | 保存位置 |
|---|---|
| 左侧六类／中间类型 | account.type_code关联目录，由目录得到group_code；分组不重复存成可互相矛盾的字段 |
| 账户名称、备注、所属银行、尾号 | assets_accounts对应字段 |
| 余额／当前欠款 | 默认position的一条assets_valuations记录 |
| 账户币种 | 初始position.currency_code；之后可在同账户增开其他币种明细，已有历史的币种不能直接改写 |
| 计入总资产／总负债 | position.include_in_totals；由side决定计入哪一边；简单账户只有一条默认明细。账户变多明细后的整体开关语义待补设计 |
| 记账时可被选择 | account.bookkeeping_enabled；目前只是预留偏好，消费／收支模块尚未接入，不生成交易流水 |
| 记录日期 | valuation.as_of_date；首版可默认当天，但应可查看、更正。recorded_at另记实际写入时间 |
| 保存账户 | 单事务创建账户、默认明细、首条估值及请求去重记录；任一步失败全部回滚 |

## 金额、汇总与历史

1. 首版建议“手动记录当前余额／估值 + 余额历史”，不是完整记账流水。股票等先录当前总市值；买入成本、股数、收益率、分红和手续费待后续业务确认。余额变化不能称为投资收益。
2. 法币金额用最小货币单位的INTEGER保存，人民币100.25元存10025，日元100存100；按币种字典精度校验。接口用十进制字符串传金额，服务端精确转整数，并约束范围；不能把健身的REAL重量字段直接照搬。SQLite的REAL是近似浮点数，依据[SQLite官方说明](https://www.sqlite.org/floatingpoint.html)。BigInt与JSON转换、汇总溢出及舍入必须在实现中明确；超出首版法币估值范围的代币数量另建高精度规则。
3. 负债金额建议录正数，由side=liability分类，在净额中减一次；授信额度不计资产，也不当作当前欠款。负余额、信用卡溢缴款、衍生品等例外需单独定义，不擅自取绝对值。
4. 不同原币不能直接相加。先按同一报告时点和明确汇率口径折算再汇总，缺汇率的项显示“未折算”，总额标为部分，不能填0或默认为1。每个结果应带汇率来源、日期、估值日期和完整性状态。
5. 历史趋势取当时已记录的估值与当时汇率；默认可沿用每项截至该日的最近值并标示旧记录。首次记录以前是未知，不伪造零余额。更改统计类别、计入开关或归档状态后若要求历史保持原口径，还需带生效日期的配置历史；未确认前不要默默重算历史。
6. 归档用于隐藏停用账户，不等于余额归零。关闭账户可先记0再归档；保留历史。永久删除与更正回溯规则尚待确认。

## 接入路径与隔离要求

建议沿用健身服务端存储方式：网页 → 共用会话取user.id → 资产字段校验 → 资产store → 同一SQLite中的assets_*表。网页不能直接连接数据库。API可采用既有Server Actions风格，未来手机/API调用同一资产服务层，避免两套计算。

- 新增 `lib/assets/model.ts`（校验）、`repository.ts`（数据库函数，可注入内存库测试）、`store.ts`（共用连接）、`summary.ts`（统一汇总）；页面暂建议 `/assets/dashboard`，路径仍需正式实现时加入登录回跳白名单。
- 所有私人表user_id NOT NULL；每次读写都按登录用户过滤。父表建立UNIQUE(user_id,id)，明细及历史使用同用户复合外键，防跨账号挂接。外键需要开启且不能替代鉴权，参见[SQLite外键文档](https://www.sqlite.org/foreignkeys.html)。
- 账户资料、余额更新均校验revision；冲突返回当前版本，不覆盖另一个窗口。请求去重检查、归属检查、版本检查与写入在同一事务内。
- 账户详情和汇总使用同一个统计函数与同一读取事务；汇总结果包括总资产、总负债、净额、类别／账户／币种分布与缺失计数。账户数量、资产条数分别统计，排除规则一致。
- 未来收支模块通过稳定account_id及position_id引用资产，不复制账号或余额；真正的转账与余额自动变动，需要统一记账事务，不能仅凭“记账可选”开关启用。ToDo和健身不自动创建或修改资产记录。
- 新建追加迁移，不改旧迁移、不重建ToDo或健身表。当前源码最高版本14；正式实现时重新检查最新版本，再分配编号，避免并行开发冲突。不要import默认lib/db来做只读方案检查，因为该模块初始化会执行迁移。

## 开发前需要明确的三个产品口径

1. 首版是否采用上述“余额／估值快照”；建议采用，完整交易记账后续做。
2. 是否保留财富总览的“同账户多明细”；建议保留，简单账户自动有默认明细，补一个“给已有账户添加明细”的入口，不强迫普通用户多填一层。
3. 默认汇总币种及汇率：建议先人民币、手动汇率并标日期；自动汇率的数据源、历史政策与更新频率另行确认。

确认后再实现结构及页面。部署前用独立测试库验证A/B账号隔离、跨账号关联拒绝、重复保存、双窗口冲突、金额精度、同银行多卡、多币种、归档和历史；迁移先在备份副本演练并比较旧表数据，再走现有备份与发布流程。本轮未改数据库。
