# 在侧 Folio · 跨设备同步

> 阅读顺序：先读[协作总则](00-总则.md)，再按任务阅读本文件。

## 采用什么方式

源码、协作文档和必要素材统一同步至用户指定的 [zqsoren/Foilo](https://github.com/zqsoren/Foilo) 仓库。两台电脑各保留一份项目，开始前取得最新内容，结束后提交并推送。代码和对应记录一起同步，下个窗口能按同一个版本接手。

**2026-11-11 首次上传已完成。** 仓库为 [zqsoren/Foilo](https://github.com/zqsoren/Foilo)，按用户明确选择保持公开；默认分支为 `main`，本地 `main` 已跟踪 `origin/main`。源码首次提交为 `b8b3254`，249 个文件已推送，并通过 GitHub API 逐一核对文件内容校验与模式。同步完成的记录随后续文档提交一起维护。第二台电脑的实际下载、登录及启动尚未验证。

GitHub 可以同步文件和变更历史。AI 的聊天记忆、本机连接、尚未保存到文件的设计改动不会跟着同步，所以仍要维护当前状态和日志。

## 哪些内容放进去

| 内容 | 处理方式 |
|---|---|
| 源码、依赖清单、数据库迁移、测试 | 同步；另一台电脑重新安装依赖 |
| `AGENTS.md`、`README.md`、`docs/` | 同步；这是不同窗口和设备共用的记录 |
| 网页运行所需素材、可编辑图标、必要设计预览 | 同步，保持文档中的相对路径可用 |
| Figma 云端设计 | 在两台电脑打开同一设计文件，文档记录链接、Page、节点及确认日期；GitHub 只同步这些记录和导出文件 |
| 只存在本机 Figma EX 的设计 | 先确认是否支持同一文件的云端访问；如不能，导出可编辑源文件到仓库中的固定路径，再提交和推送；接手前导入并核对基准 |
| 依赖安装目录、构建结果、浏览器临时记录 | 不同步；在另一台电脑重新生成 |
| 真实业务数据库、备份、密码、密钥、聊天恢复目录 | 不进仓库；两台电脑各用自己的开发数据与登录凭据 |
| 安装包、服务器发布压缩包 | 不进源码仓库；需要分发时单独管理 |

本次检查发现 `output/` 约 1.1 GB，主要是 Mac 安装构建和服务器发布包；`聊天恢复检查/` 约 611 MB。已在 `.gitignore` 排除这些生成物和聊天恢复目录，保留 `output/folio-icons/` 等既有设计引用；浏览器验收临时目录 `output/playwright/` 也已排除。排除仅影响 Git 收录，不删除本地文件，也不等于已经检查完所有文件的隐私内容。

普通 Git 仓库中，GitHub 会阻止超过 100 MiB 的文件。确需保留的大型可编辑设计源文件，应在首次提交前配置 Git LFS，或采用设计工具的云端文件。不要把整批导出包反复塞进 Git 历史。依据：[GitHub 大文件说明](https://docs.github.com/en/repositories/working-with-files/managing-large-files/about-large-files-on-github)。

## 第一次接入 GitHub

用户已指定账号与仓库为 `zqsoren/Foilo`，默认分支为 `main`。本轮已确认上传网站及 Mac 端源码、设计记录和必要素材，排除本机数据、凭据、聊天备份和生成包。仓库按用户明确选择保持公开，后续不擅自更改可见性。

1. 检查待提交清单，排除真实记录、凭据、聊天备份和生成包。`.gitignore` 只能按路径和文件名排除，不会识别写在 Markdown 或脚本里的密码。
2. 建立本地首次提交，包含源码、文档与必要素材；逐类确认收录范围。
3. 仓库已由用户创建，连接现有远端并推送，不需要再建仓库。首次上传已经获得本轮明确授权；登录由用户在 GitHub 官方页面完成。
4. 第二台电脑克隆该仓库，在自己的 AI 工具中打开克隆后的根目录。路径和文件夹名字不必与第一台相同。
5. 按项目说明安装依赖，建立独立开发数据库；核对设计文件和连接。不从第一台复制整份依赖目录、密钥或真实数据库。
6. 第一台推送后核对远端提交；第二台下载并核对总则、模块状态及素材后，分别在[项目日志](项目日志.md)记录结果，不把第一台上传成功当作第二台已配置完成。

实施方法参见 [GitHub：将本地代码加入仓库](https://docs.github.com/en/migrations/importing-source-code/using-the-command-line-to-import-source-code/adding-locally-hosted-code-to-github)。下文日常流程在首次同步完成后使用。

## 第二台电脑第一次下载

```bash
git clone https://github.com/zqsoren/Foilo.git
cd Foilo
npm ci
npm run db:migrate
npm run db:seed
npm run dev
```

在 AI 工具中打开下载后的根目录，先读[总则](00-总则.md)。本地网页打开 `http://127.0.0.1:3000/login`；新电脑使用独立的开发数据库与本地账号。依赖 Node.js 22 或更高版本，详细启动说明见仓库 README。尚未配置 GitHub 登录的电脑可以下载公开仓库，但推送修改仍需相应权限；私有仓库的下载也需要授权。

## 平时怎样接力

**开始前**：AI 先检查分支及未提交改动，再获取远端变化。工作目录干净且没有分支分叉时，用 `git pull --ff-only` 更新本轮分支；否则先辨认本地工作和分支差异，保留双方内容后处理。随后读取当前状态和规则。

**结束时**：AI 更新当前状态与日志，检查本轮变更；在已获授权的同步范围内，把代码与文档一起提交并推送。交接说明本轮分支、提交及推送是否成功；提交编号可在回复或 Git 记录中查，不要求把当前提交自己的编号写入同一次提交。

**换电脑时**：前一台推送成功，后一台拉取同一分支后接手。只提交未推送、或只留在编辑器中的内容，另一台都读不到。断网时在当前状态标注「仅本机，待推送」，恢复联网后再同步。

推荐先采用接力方式：同一模块同一时段由一个窗口主做。它需要的分支和冲突处理最少。已经切到任务分支时，后一台继续该分支，不要默认回到 `main`。

## 确实需要两台同时做时

- 按模块或任务建分支，例如 `codex/gym-mobile-plan`、`codex/landing-desktop`。每个分支只带自己的文件与记录，完成后通过合并请求汇入 `main`。
- 一个模块的当前状态注明本轮分支、窗口和涉及文件/画板。这个登记用于协调，不是跨设备实时锁；未推送的登记其他设备也看不到。
- 同一个当前状态文件、共用规则、共用代码、数据库结构或同一 Figma 画板，同一时段由一个窗口主改。需要交叉修改时，先在任务中约定范围和先后顺序。
- Git 分支不能隔离 Figma 云端画布；两个分支也可能同时改坏同一个画板。需要并行设计时，各用独立画板或副本，记录候选稿与已确认基准，评审后再合并。
- 合并时同时检查代码和三份模块记录。日志保留双方有效条目；当前状态按合并后实际结果更新；规则冲突以用户确认的决定为准。产品决定不明确时再请用户确定，不按设备日期直接覆盖。
- 旧分支的当前状态只描述该分支。合并后更新工作分支与当前状态，避免另一台继续过期版本。

GitHub 同步和生产发布分别进行。推送成功代表文件已到仓库；网站是否更新，仍按原发布流程执行和验收。

## 不同 AI 怎样读同一套规则

统一的阅读路线与记录维护要求集中在[总则](00-总则.md)，模块索引及全产品约定保留原入口，业务规则继续放在模块内。项目根目录的 `AGENTS.md` 仅引导 AI 找到总则，随完整仓库一起同步；Codex 的项目级读取方式见 [OpenAI 官方说明](https://learn.chatgpt.com/docs/agent-configuration/agents-md)。其他 AI 若不自动读取，在首次指令中直接指定总则，不另抄一套制度。

若第二台电脑只取得设计日志文件夹，直接让 AI 先读其中的《00-总则.md》，无需先取得根目录文件。它能理解接手流程并维护这些记录；源码、素材和设计源文件则按实际工作需要另行补齐。首次手动转移时注明副本日期与来源；完成工作后也需把更新后的记录同步回去，避免两台各留一份不同版本。更换设备后须重新确认工具连接和访问权限。
